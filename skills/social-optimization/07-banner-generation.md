# Generating banner/cover images — via code, never AI image generation

## Why not AI image generation
AI-generated banners are the single most common "AI slop" tell on a professional profile — cartoon avatars, floating tech-icon clip art, generic motivational text over a busy gradient. A person who's asked for optimization is very often specifically trying to get *away* from that look. Default to building the banner as real HTML/CSS and rendering it, which produces clean, typography-led, on-brand results with full control over every pixel — and reads as considered design rather than a generated image, because it is one.

## Method that worked in a real run

1. **Write the banner as a plain HTML file** at the exact target pixel dimensions the platform wants (LinkedIn cover: 1584×396). Set `html, body { width: <W>px; height: <H>px; }` explicitly rather than relying on viewport percentage sizing.
2. **Design principles**: dark background (avoid pure black — a very subtle tint reads as more considered), one bold display font for the name/headline (a Google Font loaded via `@import` works fine; a heavy grotesque worked well in one run), a muted body font for secondary text, one or two accent colors used sparingly (an accent line, a subtle radial glow), and a faint background grid for texture if it fits the person's aesthetic. Keep total color count low — 2-3 colors plus near-black/near-white, not a rainbow.
3. **Respect the platform's own UI overlap zones.** LinkedIn's circular profile photo sits bottom-left over the banner — right-align (or otherwise offset) the main text so the person's photo never covers their own name. Check the actual rendered profile, not just the raw banner image, to confirm nothing gets covered.
4. **Render it**: browser file:// and data: URL navigation are both commonly blocked by automation sandboxes. The reliable path: serve the HTML via a throwaway local static server (e.g. `python -m http.server <port>` from the file's directory) and navigate the automated browser to `http://localhost:<port>/<file>.html`. Resize the browser viewport to the exact target dimensions before navigating, then take a viewport screenshot (not full-page) — this produces a pixel-exact image at the right size with no cropping needed.
5. **Strip automation-tool watermarks before the final screenshot.** Browser automation extensions sometimes inject a small floating badge/icon into the page. Don't remove elements by a loose bounding-box heuristic (this can accidentally delete real content that also happens to sit near an edge) — instead remove only elements with `getComputedStyle(el).position === 'fixed'`, which reliably targets injected overlay widgets without touching normal page content.
6. **Cache-bust between edits.** If you edit the HTML and re-navigate to the same local URL, the browser may serve a stale cached version — append a throwaway query string (`?v=2`, `?v=3`, ...) on each re-render during iteration.
7. **Save every version** the person sees or reacts to, not just the final one — under something like `.tmp/banner/<platform>_banner_v<n>_<description>.png` plus the source `.html`. If the person asks for a change (e.g. "flip it, right-align the text instead"), edit the same HTML file and re-render as a new numbered version rather than overwriting silently — they may want to compare or revert.

## Uploading it

Try the real upload flow via browser automation first — it can work end-to-end (find the edit-image button, which typically opens a small menu, then a specific "Change/Upload photo" action, which triggers a real OS file-chooser event; use the file-upload tool once that file-chooser modal state is confirmed present). But some sandboxed automation environments hard-block the literal file-selection step at the protocol level (a "Not allowed" error on the underlying file-input call) even after successfully reaching the real chooser dialog — if that happens, it is a genuine environment restriction, not a mistake in the approach: hand the finished image file and exact click-path to the person to upload themselves, rather than continuing to retry the same blocked call.
